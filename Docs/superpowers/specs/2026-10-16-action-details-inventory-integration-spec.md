# 行动详情、地图入口与物品交易统一 Spec

日期：2026-10-16
状态：本窗口交付的施工规格；工程尚未完成，不代表运行验收通过。
用途：交给一个工程 Agent 串行实现公共能力，供后续五批文案配置复用。

## 1. 目标与范围

玩家点击地点，在同一套行动详情中看到剧情、进入咖啡馆、购买/交换、交付等行动。每张卡能解释“做什么、能否执行、缺什么、付出什么、明确能获得什么”。策划通过现有 NCS/Luban 源表配置，不能每新增一篇剧情就在界面或 DayFlow 中新增剧情 ID 判断。

本轮交付：六类行动及组合语义、条件和成本分离、统一导航卡、交易/交付、物品栏联动、红点/必做/日结一致性、配置校验、调试和实际验收。复用现有美术模板，不重做地图、不制作网页编辑器、不新增平行剧情调度或钱包。

普通剧情继续由已有 NCS Event/Presenter/Panel 播放。早晨、经营后、夜前的自动事件不强制包装成地图行动；只有需要玩家从地点主动打开的内容才挂行动卡。

不把本轮扩展成18根剧情全部放行。正文、金额、日期等未定项保留明确门禁；公共能力要用可执行验收样例证实，不能因个别剧情未定就只交接口。

## 3. 统一卡片与配置概念

### 3.1 行动做什么与多久能做一次分开

新增或复用一个明确的执行类别字段 `executionKind`：

| 类别 | 执行含义 | 约束 |
|---|---|---|
| Event | 启动已有NCS事件/有序事件链 | 不复制对白，不创建新的剧情系统 |
| Navigate | 调用已注册的游戏导航入口 | 本轮用于进入咖啡馆；0AP、零物品/资金成本，不发剧情奖励 |
| Exchange | 确认一笔采购、出售或物物交换 | 成本与所得同步提交；交易确认不要求播放一段虚构剧情 |
| Delivery | 提交固定一组物资，积累进度 | 沿用累计/连续每日交付及里程碑能力 |
| EndDay | 请求结束当前一天 | 复用正式DayFlow和必做检查，不能直接改日历 |

六种旧行动类型继续作为频次/期限/进度规则。类别不从标题、地点中文名、剧情ID猜测。旧行动缺省按已有语义迁移为Event或Delivery；旧endDay显式映射为EndDay。

### 3.2 三种条件必须分离

1. 出现条件：日期、已解锁、前置剧情等。不满足时不显示，不产生新内容红点。
2. 执行资格：属性门槛、持有但不消耗的物品、状态条件等。不满足仍显示卡片，并逐项说明原因。
3. 消耗：物品数量、行动点、唯一经营货币。消耗不足仍显示卡片，显示“当前/需要”。

同一张卡允许免费、无资格要求。条件缺数据不当作false或0静默处理：禁用并显示普通玩家能理解的“暂不可用”，具体缺键只在GM/日志展示。

已有Condition表的 `ownerType=action`保持原显示语义；新增清晰作用域（建议 `actionExecute`）用于执行资格，完整接入schema、loader、validator和解释器。复用Condition现有AND/OR/比较符，不复制解析器。资金与成本不足不能写成显示条件。

默认列表最多显示6项“资格+消耗”；加载时校验展示后的总数，不截断。出现条件无需全部展示，防止剧透。条件表达式若含OR，应显示一个准确的“任一满足”组，不能把各项错误显示为全部必需。成本为正整数，重复物品/AP/资金项合并检查与展示。

### 3.3 配置字段合同

保留Action现有字段：actionKey、type、mustExecute、nameText/descText、requirements、resultEvents、durationDays、progressTarget、nextActionKey、deliveryMode、replacesLocationActions、focusLocationOnComplete。

补齐以下语义，建议字段名如下；工程可复用同义字段，但必须在最终配置说明给出唯一对应，不允许重复标准：

| 字段/关联 | 语义与默认 |
|---|---|
| executionKind | 上述执行类别；旧数据按迁移规则补齐 |
| navigationKey | 注册导航命令，如 cafe.enter；只允许白名单，不填任意场景路径 |
| executeTextKey | 按钮文字，可缺省为继续剧情/进入/购买/交付/结束一天 |
| sortOrder | 地点内稳定排序；相同值用源行顺序，不能刷新时随机跳卡 |
| action显示Condition | 沿用已有ownerType=action |
| action执行Condition | 新作用域，提供逐条满足状态与人类可读名称 |
| requirements | 消耗；保留Item(key,n)、ActionPoint(n)，增加Money(n)，Money固定映射唯一经营账户 |
| successResultOwnerId | 可选，引用现有Result表的一组结果；交易用于一次提交，不能另造奖励表/结算器 |
| onExpireEvents | 过期事件，与主动完成resultEvents分离；空则只过期移除 |
| onExpirePolicy | Remove / RunEvents；显式迁移旧Timer，不依赖含糊默认 |
| notifyNew | 是否参与新内容提示；普通剧情/新交易默认true，常驻导航默认false |

交易卡的“获得”区来自实际successResultOwnerId，可显示物品数量或售价所得。剧情卡不默认展示隐藏分支奖励。新增Result owner的引用必须由正式校验认可，不能造一个永远不会播放的假Event只为了存奖励。

补齐/复用物品元数据：稳定itemKey、nameText、iconPath、description、归属库存类型（MapInventory / CafeSupply）。元数据不另存数量。图标缺失用明确通用占位；正式玩家界面不显示裸key。

同一actionKey在多个地点继续共享进度/完成状态；若需要两个独立实例，配置两个key，本轮不改成隐式按地点分裂存档。

## 4. 六类行动的确定语义

| 类型 | 规则 |
|---|---|
| Repeat | 当日可重复，每次独立检查/提交成本与结果 |
| Daily | 每个正式游戏日最多成功一次；失败/取消不占次数 |
| Once | 整个存档仅成功一次；点击/打开/看完部分对白不算完成 |
| Timed修饰 | 挂载日+d天到期；到期后不可执行，移除或运行明确过期事件 |
| Progress修饰 | 每次有效提交加1，未达目标不触发最终成功事件；达到目标只触发一次 |
| Future | 倒计时卡不可执行；到期移除、挂载nextActionKey并触发配置事件一次 |

Repeat/Daily/Once互斥；Timed和Progress可叠加基础类型；Future与其余类型互斥。无基础类型的Timed/Progress沿用已定义可重复提交语义。Once+Progress中每次提交只加进度，达到目标才算Once完成。EndDay不与Progress/Future/Timed或成本组合。

保留旧类型别名加载，但新配置统一用REPEAT/DAILY/ONCE等明确标准值：旧Once（每天）与ONCE（一次性）必须在文档列出，迁移不得改写旧值含义。

计时样例：day3挂载durationDays=2，day3/4可操作，day5到期。存读档、重复BeginDay、跳日都不能重复执行到期结果。到期事件失败须留可重试记录，不能先删除所有痕迹；Future替换与到期回执需保证幂等，不出现两张后续卡。

到期任务复用NCS同一调度队列：尊重目标Event声明入口、priority和安全边界，不经地图点击接口强行启动Morning/BeforeNight事件。声明MapAction的事件不能自动播放，配置校验拒绝这种到期绑定。显式到期请求可授予资格，但不能绕过事件前置条件/blockedBy。

普通Progress每次成功提交都支付整组成本。累计每日交付一天一次；连续交付漏日按现有规则重置进度，不退还历史交付，不重复发已发里程碑奖励。最终交付有后续演出时，提交已成功的物资不因关闭展示而重新扣一次。

必做行动不能配置Future或会在当天中途消失的期限；会阻止日结的行动必须存在可达地点、有效执行路径。静态可判定冲突直接报错，不让玩家进入确定的死锁。

## 5. 咖啡馆、剧情与结束当天

### 5.1 咖啡馆导航

正式配置一个cafe.enter导航行动，挂到权威cafe地点；MapActionDetailsView从统一配置创建卡片，删除重复硬编码插卡分支。导航执行委托现有MapSceneController/DayFlowController入口，不直接LoadScene绕过校验。

点击地点只聚焦并打开详情；玩家再点“进入咖啡馆”才进入。0AP、没钱、没物品不影响免费导航。加载期间防连点，失败留在可操作界面并说明原因；进入不重置新游戏、不产生剧情完成/奖励/耗日记录，不把每次导航当新内容。

场景/地图中文别名只在现有兼容映射处处理，不能把真实市场“大堂区”误判为咖啡馆。正常游戏有可展示行动的非咖啡馆地点同样能打开详情；新手期继续遵守原有地点/UI锁定。

10月7日既有例外必须回归：S1未完成时咖啡馆仅显示剧情卡；完成后返回地图→聚焦咖啡馆→展开正常导航/经营入口，由玩家点击。不能自动开店。replacesLocationActions只隐藏同地点其他卡和导航，不关闭其他地点的支线。

### 5.2 剧情与必做

新故事通过行动挂载与条件接入，不硬编码事件ID。获得赏识等历史事实使用既有NCS条件，既可控制卡片出现，也可控制根内页面；不要把根内可选人物段误当整个行动的必要条件。

必做剧情mustExecute=true、无成本、排除事项面板，未完成阻止日结。其他AP支线同时可见可选。已完成/未解锁/已失效行动不阻日结。

“结束当天”在事项面板、咖啡馆、地图的所有入口调用同一检查。遇必做未完成，提示“有需要进行的行动”，聚焦/高亮对应地点并展开卡；不自动启动剧情，不推进日期。若当天有多个必做，稳定选择第一个；完成后再次检查下一个。后台状态变更后立即刷新。

事项面板只收录已开放、带AP消耗的非导航行动，仍可显示其缺物/资格信息；结束当天按钮作为常驻控制保留。0AP必做剧情与普通导航不被自动塞进事项列表。

## 6. 采购、换物与库存归属

### 6.1 本轮必须交付的交易

固定一份商品/物资包为一次执行单位，本轮不做完整商店、购物车和任意批量输入。可重复行动可以连续购买，每次都重新校验与结算。

- 采购：Money(n) → ItemAdd(item,q)。
- 物物交换：Item(a,n) → ItemAdd(b,q)。
- 出售：Item(a,n) → MoneyAdd(n)。
- 交付：Item/ActionPoint固定成本 → 进度/里程碑/最终结果。

卡片清楚显示“消耗”和“获得”，余额/物品不足仍可见。发奖不在UI回调直接加库存；统一走正式执行服务和NCS结果预检。禁止同一成本在requirements与Result再次扣除；同一物品作为明确输入和输出可以合法存在，但预检按实际输入库存检查，不能拿本次未来产出凑成本。

### 6.2 钱与经营原料

经营货币只有一个真实账户，沿用CafeNarrativeValueProvider/INarrativeMoneyAccount。物品栏中的金币是此余额的投影，不新建item.gold库存；本轮用“金币”显示，如项目已有权威名称则沿用。

剧情物品进NarrativeMapInventory。经营原料必须映射到FreeCafe真正能消耗、会保存的库存来源；不能只在地图库存加一份同名咖啡豆就声称可用于经营。

工程先核对现有FreeCafe补货/BuySource和实体库存生命周期，选择一个已有可用原料，完成地图购买→实际库存增加→进入经营取用→保存恢复的验证。通过明确provider/适配器复用领域入口，不修改Packages框架、不直接改任意场景物体字段。

若正式经营会话不在地图存续，需要建立由现有存档owner持有的合法入库交接记录，保存且在经营库存准备好后仅应用一次；再次开店不丢失也不重复补货。无法确定权威库存/计量单位时禁止发布该商品并明确报告，本轮不得伪造成功。地图背包交易和咖啡馆导航可先独立完成。

测试交易价格/数量只放隔离夹具，不自动把虚构商品、低价样例或无限套利行动加入正式地图。真实采购行动采用内容owner确认的数据；暂未定价不阻碍公共能力验收。

## 7. 成本、结算与取消的硬约束

目标：任何失败都不能只扣成本不给物品；任何重复点击/回调/恢复都不能再扣一次或再给一次。

执行状态至少能区分：Idle、Checking/Presenting、Committing、Committed、Failed/Cancelled；每次操作绑定稳定operationId及行动实例/日期，结果回调需校验owner和版本。

- 动画不扣库存。动画后再次检查正式余额、库存、AP、日期、解锁和目标有效性；旧UI快照不具备支付权。
- Exchange：统一预检成本、所得、库存容量/整数溢出及provider可用性；成本、所得、计数和回执同次成功或无修改。明确禁止“先扣钱，稍后给物品，失败仅报错”。
- Event行动：演出取消/启动拒绝时不扣动作成本、不写动作完成。将行动成本接入当前根成功提交边界，与该根奖励共同预检。演出期间外部资金变化引发不足时，拒绝全部提交，保留可重试状态，不发出虚假完成提示。
- 有序多事件链：已成功的前序根不回滚、不重播其结果；保存链游标。每次行动成本只提交一次（与第一个成功根一起），仅剩余根重试；在任何根成功前取消则零消耗。卡片明确显示“继续未完成行动”，根全部成功才计行动完成。不得声称这种多根链是全链原子事务；要求全链取消零修改的剧情必须配置为一个根内多页。
- Delivery/Progress：每次交付成本、进度、触发里程碑资格和提交回执一起提交；已提交后取消通知/奖励演出不退交付也不重新收取。未完成通知或最终事件保留可恢复队列，最终事件成功前不显示整项全部完成。
- 中途关闭详情/切场景不得让失效回调继续操作UI或重扣。提交前可以取消，提交完成后的返回只是关闭展示。
- 读档恢复计数、每日记录、到期、动作链游标与交易回执。提交的同步临界区禁止存档；跨演出存档遵守原NCS blocksSave/检查点政策，不另建一份剧情保存器。
- 跨经营账户/背包/provider的提交必须有失败恢复策略并测试拒绝注入；不能假定预检后每个TryCommit永远成功。用现有事务/owner扩大提交边界或提供可靠撤销，避免通知重入观察半笔交易。

## 8. 卡片与物品栏表现

保留正式Prefab的布局风格，扩展已有模板，不另建平行Canvas/临时Scene。标题、描述、类型、期限/进度、资格、成本、所得、按钮是同一张卡的可选区域，无内容区域收起。

- 每项资格/成本单独显示当前值、所需值、名称、满足/未满足标识；颜色之外有文字/图标，不能只把整块字一起变红。
- 最多6项两列排布，长中文可换行，卡片自动适配并可滚动；卡片切换/翻页不能丢当前焦点。
- 禁用状态仍可请求查看原因：说明缺什么并轻震对应项；Future显示剩余天数，Daily显示今日已完成。提交中真正禁止重复点击。
- 成本动画：物品栏项先滚入视野，再飞向对应成本格；金币从余额位置、AP从AP位置飞入。只作表现，不负责结算；无动效/缺图标时功能仍可完成。
- 交易提交成功后刷新库存/余额并显示准确变更，所得可飞入库存位置；取消或失败不播放“已获得”的成功反馈。
- 物品栏显示真实数量、0数量项按统一策略收起、余额不负数。同名不同key不混用；鼠标悬停/点击可查看名称描述，不能只靠缩略图辨别。
- 新卡可见时地点提示红点/感叹号；只有实际展示过对应卡才消除该卡未读标记，打开地点但未翻到该卡不算已读。已读不等于完成。余额变化不会不断制造“新内容”；Future解锁新卡会提示。

## 9. 配置迁移与校验

工程先备份现有源表并记录基线；串行修改共享Excel/schema/生成物，保留并发窗口已有修改。不要重置/清理别人文件，不批量移除剧情blockedBy。
