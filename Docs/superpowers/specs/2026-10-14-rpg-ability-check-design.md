# RPG 能力检定系统 Spec

日期：2026-10-14。状态：核心规则已获用户确认，待用户审阅。本文件只定义设计，不含实现计划或代码修改。

## 1. 目标

提供通用 RPG 能力检定：NCS 在叙事节点请求检定，系统读取玩家当前能力值并返回成功/失败；演出层显示条件与结果；NCS 根据结果播放局部内容，并可通过既有结果系统修改世界状态。首个使用场景是《文案-新手教程.docx》中顾客 B 的知觉检定。

这不是新的剧情调度器，也不是只服务知觉的特例，而是适用于任意已注册玩家能力的通用功能。

## 2. 设计原则

- **NCS 仍是整体叙事来源。** 事件、选择、进度、状态、触发器和结果负责故事长期演化。
- **检定是局部决策。** 它回答当前行动成功还是失败，不把全游戏改写成预先铺开的成功/失败大树。
- **长期影响走 NCS。** 检定本身不改值；需要影响以后内容时，由成功/失败分支执行普通 NCS Result，再由 NCS 正常触发后续事件。
- **单一事实来源。** 玩家能力从现有玩家/NCS 运行时读取，不复制检定专用属性。属性 ID、显示名、当前值来自现有配置和运行时接口。
- **确定性。** 第一版不掷骰子、不抽随机数；按判定时的能力值比较。
- **叙事与数值分工。** 内容作者写成功/失败剧情文本；能力 ID、门槛和系统提示来自检定配置及程序，不让文案手写数值或富文本标签。

## 3. 概念边界

| 概念 | 含义 |
|---|---|
| NCS 可用条件 | 决定事件或普通选项是否出现/可选，沿用现有条件语义 |
| 能力检定 | 叙事节点发生后，按玩家当前能力值计算一次成功或失败 |
| 检定结果 | 本次调用的只读快照，含 check ID、各条件当前值/门槛及总结果 |
| NCS 后续结果 | 成功/失败分支里的普通 NCS Result，负责所有持久状态变化 |

检定条件不能被当作选项解锁条件。能力不足时，玩家仍可选择/触发检定，随后播放失败分支。需要锁定选项时仍使用普通 NCS 条件。

## 4. 检定规则

### 4.1 条件和分组

每条条件引用一个稳定能力 ID 和整数门槛，第一版比较符固定为 `>=`：当前值达到门槛即通过，低于门槛即不通过。使用该能力已有的合法范围，不另定范围。

支持多个条件，分组语义沿用现有 NCS 条件：**同组全部满足（AND），组间任一组满足（OR）**。

```text
组 1：知觉 >= 3 且 智慧 >= 2
或
组 2：语言 >= 4
```

例中组 1 全通过或组 2 通过，检定成功。配置工具和 UI 必须能读清组关系。第一版不支持任意嵌套布尔表达式、加值修正、骰子或概率。

### 4.2 判定时机

NCS 到达检定节点时只执行一次，读取当时的玩家能力快照。UI 和剧情分支共用该结果，不得再次读取属性而造成显示与剧情不一致。保存/恢复已完成检定的演出时，恢复同一结果，不重算、不重复应用结果。

## 5. NCS 接入和叙事流

检定可以绑定在普通选项点击后，也可以是脚本化自动检定节点。教程老太太段落属于自动节点，不要求新增玩家选项。两种入口共用检定服务、配置与结果格式。

```text
NCS 条件满足，事件/选项出现
 -> 玩家选择，或剧情到达自动检定节点
 -> NCS 请求 checkId
 -> 检定服务读取能力并返回结果快照
 -> 演出显示条件与成功/失败
 -> NCS 播放对应内容
 -> 两支可以汇合；也可执行普通 NCS Result
 -> NCS 按更新后的状态/进度决定未来事件
```

成功/失败是局部岔路，不要求复制后续剧情。扩展现有 NCS 内容/演出表达能力，不另建永久剧情树或第二套事件队列。配置须稳定引用 `checkId`、成功/失败内容及可选 NCS 结果归属；实际表结构应在实施计划阶段依据当前 NCS 代码和工作区中的配表改动确定。

检定服务只读能力并返回结果，不直接修改 Bar、Flag、关系、物品或经营状态。需要长期影响时由对应 NCS Result 写入，沿用现有 NCS 事务、存档和触发规则。

## 6. 前端表现

> 2026-10-15 更新：“初来乍到”和“重新启航”中的自动检定表现以 [补充 Spec](../../FirstArrivalAndPassiveChecksSpec.md) 为准：成功分支首框右下角显示属性门槛和提示词，失败无提示，不另播结果正文或增加确认。其他检定入口及判定规则维持本文定义。

未执行时，在检定选项下方或自动检定说明处自动显示条件：

```text
观察老太太
知觉 >= 3
```

多条件按组显示 AND/OR。系统行由本地化能力名、比较符和门槛组成，剧情文本不负责拼接。

执行后基于同一结果快照显示成败及实际值，例如：

```text
知觉 4 >= 3，检定成功
知觉 2 < 3，检定失败
```

成功/失败须有明确文字或状态视觉区分，不能只靠颜色。UI 负责排版，不计算结果。沿用现有 Dialogue/NCS 演出链路；实现时按现有界面选择复用/扩展组件，不另做全屏剧情 UI。

结果至少保留到当前分支演出结束，但不是永久玩家属性或剧情事实。未来剧情若需记住结果，必须由 NCS Result 显式写入既有状态。

## 7. 配置和校验

配置使用稳定 ID，而非显示文本或 GameObject 路径。逻辑上至少包含：唯一 `checkId`；一条或多条能力条件（能力 ID、门槛、组号）；NCS 选项或自动节点归属；成功/失败内容引用；可选的成功/失败普通 NCS Result 归属。未配置状态结果时不产生持久状态变化。

能力显示名取现有玩家能力配置/本地化；动态当前值和门槛作为 UI 参数，不写入文案表。沿用 Luban Excel -> 生成 C#/JSON 的管线，不建立第二个手写 JSON 事实源。

校验器至少拒绝空/重复 checkId、未知能力 ID、无条件或空条件组、非法门槛、缺失成功/失败内容、错误 NCS owner 引用及不可解析的分组。错误指出具体 ID/字段；非法配置不能静默当作检定失败或播放半套分支。

## 8. 失败处理与存档

- 缺少玩家运行时、能力未注册、无法读取能力或配置非法：报告明确错误，不伪装成检定失败、不选择任一剧情分支、不执行 NCS Result。
- 检定快照是当前 NCS 演出事务的局部数据。只有普通 NCS Result 写入的状态进入现有存档；不增加永久检定历史表。
- 检定后、分支播放期间存档/恢复，须恢复原快照和待播分支，不能重复应用结果或改走另一分支。沿用现有 NCS active/pending 存档；若当前机制表达不了，实施计划列明最小改动。
- 取消、结束会话、切场景或读档替换会话时，旧回调不得提交分支或影响新会话。

## 9. 第一版不做

- 随机骰子、概率、暴击、大成功/大失败。
- 临时加值、装备修正、团队协助、优势/劣势、重掷。
- 任意嵌套布尔表达式编辑器。
- 检定专用永久历史或平行剧情调度器。
- 因能力不足而自动禁用选项；锁定仍由普通 NCS 条件处理。

## 10. 验收标准

1. 教程 `player.perception >= 3`：值为 3 或更高走成功文本，低于 3 走失败文本，两支按文案汇合且不重复播放。
2. 多条件检定满足组内 AND、组间 OR；等于门槛时成功。
3. 能力不足不阻止进入/选择检定；真正的 NCS 锁定条件仍正常工作。
4. UI 显示的当前值、门槛、成败和剧情分支来自同一结果快照；多条件关系清楚。
5. 检定不改能力、不直接改 NCS 状态；配置的普通 NCS Result 只执行一次，其状态可被后续 NCS 条件/阈值读取。
6. 无状态结果配置时只影响局部叙事；成功/失败后可汇合。
7. 无效 ID、运行时缺失和错误内容引用均有明确诊断，不静默走失败分支。
8. 保存/恢复进行中的检定分支不重算、不重复执行结果，也不接受旧会话回调。
9. 不使用随机机制；同一能力状态下同一检定结果一致。
10. 测试覆盖核心判定、配置校验、展示和恢复，使用现有 NCS/演出测试入口；画面回归遵守项目共享 `Assets/Scenes/PresentationDebugScene.unity` 约定，不另建临时演出场景。
