# 条件系统简化与每日交付、GameOver 接入 Spec

日期：2026-10-13。用途：交给后续开发 agent 实现。本轮只编写设计，不修改游戏代码、配置表或玩家存档。

## 1. 目标与范围

用一个简单的 bool 条件池替换旧的复杂条件判断。物品数量继续由物品栏保存，行动交付进度继续由行动保存。事件、选项、行动和结局共用查询入口，不重复保存物品或进度。

用户已确认：

- 剧情条件主要是 bool，例如拥有专精、NPC 已死亡、知道某个秘密。
- 同种物品堆叠，不同钥匙使用不同物品 ID；不需要逐件物品实例。
- 交付可以要求多种物品，但按天交付固定一份，每天最多一次，每次扣行动点。
- 按天交付支持累计和连续两种模式。
- 默认全部完成后触发剧情，也保留可选的中途提交次数节点。
- 判断支持简单 AND / OR。
- 第一版结局显示游戏结束面板，通过游戏流程进入 GameOver。
- 旧开发存档不要求全面历史兼容，但当前自动存档应尽量能继续进入游戏测试。
- 旧条件代码可以简化、移除、重构；不要为了兼容废弃设计继续堆复杂逻辑。

第一版采用以下明确默认值，不扩展成额外配置：连续漏一天重新计数；已消耗物品和行动点不返还；中途剧情同一行动只触发一次；结局面板按钮返回主菜单；多个结局同时满足按优先级、再按稳定 ID 选择一个。这些默认值是为了让实现可执行，不代表用户要求新增对应配置功能。

本轮不做：NPC 多状态模型、专精等级、跨周目条件、自由数量分批交付、任意脚本表达式、条件过期、复杂连续中断策略、可重复领取同一交付委托、通用事务/历史数据库、结局演出系统、全项目 FSM 重写。

## 2. 大白话模型

| 数据 | 回答的问题 | 保存在哪里 |
|---|---|---|
| bool 条件 | 张三死了吗？主角有咖啡专精吗？ | 新条件池 |
| 物品数量 | 我现在有多少药品？ | 现有地图背包 |
| 交付进度 | 这个行动已成功交了几天？今天交过吗？ | 行动状态 |
| 数值 | 当前属性或关系值是多少？ | 现有 NCS Bar |
| 事件完成记录 | 某个事件已经发生过吗？ | 现有 NCS 事件记录 |
| 结局结果 | 当前会话是否已结束、选中了哪个结局？ | 会话叙事快照 / GameFlow |

检查不会修改数据。交付和事件结果才会修改数据。

“有钥匙”不需要额外存一个 bool；直接检查背包数量 >= 1。“曾经交付过钥匙”如果影响剧情，则由对应事件设置一个独立 bool。两者含义不同。

物品增加、扣除、读档恢复和 UI 显示都使用同一份数量。不得在条件池复制数量或建立另一份物品实例列表。

## 4. bool 条件池

### 4.1 内容与标识

一个稳定 key 对应一个 bool。建议约定：

| key 示例 | 含义 |
|---|---|
| `npc.npc_b.dead` | NPC B 已死亡 |
| `specialization.player.coffee` | 主角拥有咖啡专精 |
| `story.secret_known` | 已知道秘密 |
| `story.npc_b_helped` | 已完成救助 |

key 是标识，不是显示文案；显示名使用现有 Text。人物专精需要区分角色时，将角色 ID 放入 key。无需新建 scope 对象、多状态容器或专精等级。

已定义但尚未设置的条件使用配置初始值，通常 false。设置相同值不产生一次新变化。清除普通条件等于设为 false。

NPC 死亡使用 bool 就够。死亡类条件在普通玩法中只能 false -> true；本版不支持事件复活。新游戏重置、读档还原不算复活操作。可以在条件定义上保留一个简单“只允许变为 true”字段，死亡条件启用，其余条件关闭。

死亡不会自动执行所有世界变化。若剧情需要移除 NPC、关闭行动或改变地点，仍由现有 NCS 结果或明确的前置条件配置负责，不能把“NPC 不在场”推断为死亡。

### 4.2 唯一来源

条件池由会话级叙事状态拥有，和 `NarrativeSnapshot` 一起保存，不依赖某个面板或场景生命周期。

保留一个小的读取/修改边界即可，例如“读取 bool、设置 bool”。不要求 CQRS、事件溯源或复杂服务架构。

人物详情、行动检查、事件和选项检查、结局检查都读取这个池。专精不再使用“profile 列表 OR flag”两份来源。旧列表只参与一次存档迁移，随后不再拥有运行时专精。

旧 `event.locked.*`、`trigger.once.*`、`date.once.*` 等内部记录不能被剧情内容当作普通条件任意清除。可以保留内部存储，或者整理为独立内部字段，但不进入公开条件目录。

### 4.3 简单配置

在 Narrative.xlsx 增加一个小的 `ConditionKey` sheet，列出 `key`、`nameText`、`initialValue`、`onlySetTrue`。这是 bool 定义表。

现有 `Condition` sheet 仍是“判断要求的行”，不是 bool 池。它的 `conditionId` 是配置行 ID，不能当作事实 key。

引用未知条件 key 必须报配置错误；不能把拼错的 key 当作 false，再通过“要求 false”或 NOT 变成可用。定义完整校验失败时明确报告，不能启动带错误数据的条件判定。

## 5. 简单条件判断：AND / OR

继续使用现有 groupIndex，不增加括号表达式或脚本语言：同组所有行必须满足（AND）；不同组满足任意一组即可（OR）。

例：有钥匙，或者有开锁专精。

| owner | groupIndex | 检查 |
|---|---:|---|
| 房门行动 | 1 | 钥匙数量 >= 1 |
| 房门行动 | 2 | 开锁专精 = true |

例：张三已死亡，并且玩家有遗书。

| owner | groupIndex | 检查 |
|---|---:|---|
| 某结局 | 1 | 张三已死亡 = true |
| 某结局 | 1 | 遗书数量 >= 1 |

第一版新查询仅需：

| 检查类型 | 读取来源 | 配置含义 |
|---|---|---|
| `BOOL_EQ` | bool 池 | 指定 key 等于 true 或 false |
| `ITEM_GTE` | 地图背包 | 指定物品数量至少多少 |
| `ACTION_PROGRESS_GTE` | 行动 | 当前有效进度至少多少；累计看累计次数，连续看当前连续次数 |
| `ACTION_COMPLETED` | 行动 | 指定行动已完成 |

现有仍有内容使用的 Bar 比较和事件是否发生可以保留为小型只读查询：`BAR_GTE`、`BAR_LTE`、`BAR_BETWEEN`、`REL_GTE`、`EVENT_HAPPENED`、`EVENT_NOT_HAPPENED`。Bar/关系数值不搬进 bool 池。事件记录也不复制成可写 bool。

旧概率条件、角色/地点/时段上下文条件、触发次数表达式、重复 op/notFlag 语义等不属于本版需求；移除前检查实际配置并迁移或明确报告不支持。日期调度和 Actor/Target 演出身份继续保留，它们不因删除对应判断而被删掉。

新 BOOL_EQ 直接填写预期值，不同时再填一个 NOT。旧 FLAG_SET / FLAG_CLEAR / notFlag 在内容迁移时化简；不要保留两套对同一行的解释。op 的实际语义由保留的查询类型决定，删除无用字段或禁止填矛盾值。

事件、选项、行动使用同一个判断入口。没有条件行表示无额外限制；有行但数据非法表示配置错误，不表示无条件通过。结局没有条件行则校验失败，不允许开局直接触发。

行动的“需要持有物品”放在只读条件行；“需要交出物品”和行动点属于消耗配置。OR 只影响是否允许执行，不影响扣除哪份成本；所有明确配置的成本都要满足并扣除。本版不支持“交药品或交食物任选一种”的替代成本。

## 6. NCS 结果修改

继续使用原有事件和选项调度，面板只消费展示快照，不自行改条件或扣物品。

bool 结果可复用 `SET_FLAG` / `CLEAR_FLAG` 这两个现有名字，但执行必须指向新 bool 池，不再旁路写另一份旧状态。SET_FLAG 仅接受 true/false，死亡类条件的非法清除应被校验拒绝。

增加简单物品结果：`ITEM_ADD`、`ITEM_REMOVE`，目标是物品 ID，值是正整数；均调用同一背包入口。移除数量不足时失败并明确报告，不能减成负数、静默扣一部分或假装事件正常完成。对同一次事件及所选选项的 bool/物品结果，按实际执行顺序在临时值上预检，包括重复扣除和先增后减；预检通过才提交这批数据，失败不部分修改 bool/物品、不标记事件正常完成。无需建立通用跨系统回滚引擎；已有 Bar、演出和场景结果继续沿用原边界，异常必须留下可定位的事件/结果 ID。

同一个交付行动已扣过的物品，不得在它的完成 Result 中再扣。配置校验对明显重复扣费给出提示，示例内容不使用这种写法。

内部锁事件、once 标记等保持内部功能，不能因为名字也叫 Flag 就和公开 bool 条件混写。

## 7. 每日固定交付

### 7.1 配置与示例

复用现有 Action，新增最少字段 `deliveryMode`：`None` / `Cumulative` / `Consecutive`；复用 `progressTarget` 表示所需成功天数。不要把旧的 `type=Progress` 或自由重复次数自动解释成每日交付，迁移必须明确。

交付模式下，每次固定成本继续用现有要求里的 Item 和 ActionPoint 表达；这两种只是消耗，其他只读判断收敛到 Condition 行的 ownerType=action。

示例：每次药品 2 份＋食物 1 份，行动点 1，目标 5 次，每天最多一次。

- 只能整份提交，不让玩家自由选择 1 份或 10 份。
- 有大量库存也不能同一天提前交完后续几天。
- 每个行动每天最多一次；不是全游戏每天只能交一个行动。
- 两个行动需要同一种物品时各自扣费、各自计数。
- 物品或行动点任何一项不足，整次不扣费、不增加进度。
- 同一物品配置多行时先合并数量检查，防止逐行看都够、合起来却不够。
- 非交付行动维持原本的可重复/每日/一次性规则，不强制全部变成每天一次。

### 7.2 进度

保存必要状态：actionKey、有效进度、最后成功提交日、是否完成、已触发节点 ID。最后提交日可以判断今天是否已经提交，无需再保存可矛盾的 todaySubmitted bool。

累计模式：漏一天保留进度。成功提交一次 +1，达到目标完成。

连续模式：相邻两次成功提交的正式日序相差 1，进度 +1；漏一天后进度归零，后续提交从 1 开始。同一天再点直接拒绝。换天、跨多天跳转或读档后必须更新有效连续进度，不能只在下一次点击时才处理，否则 UI 和结局会读到过期进度。

完成后不再因漏天重置，不再扣费，不再提交。首次领取/挂载只是开始接受交付，本版不要求从挂载当天必须交付，也不允许关闭重开面板改变进度。

连续中断固定重新计数；不退款、不自动失败，不增加额外策略配置。

### 7.3 中途与完成剧情

增加可选 `ActionMilestone` sheet：milestoneId、actionKey、atProgress、eventId、seq。目标是现有 NCS Event。完成剧情继续使用现有 action.resultEvents，不另做剧情播放器。

达到中途次数时触发一次，最终次数触发完成结果。中途节点限定 1 <= atProgress < progressTarget，防止与完成结果重复。

中途记录跨天、跨读档保留。连续中断后重新达到同一节点不重播。未配置中途节点的行动只在完成时触发结果，不每次提交都弹剧情。

一次正常成功提交只增加一次进度，不支持库存换多次进度。由此没有“一次交付跨越好几个节点”的自由数量逻辑。

提交和剧情排队期间禁止再次执行同一行动。扣费、进度、节点标记和待播放事件作为同一个可恢复行动状态保存；读档恢复演出不得重复扣费、推进或发奖。异常演出不能当作成功完成，不做通用演出失败退款。

### 7.4 UI

行动详情至少显示：每次需要的全部物品与数量、每次行动点、累计/连续模式、有效进度 x/N、今日已交付或完成，以及不足原因。

今日完成提交后按钮不可再执行；可保留当前点击提示方式。不能根据库存绘制“今天还能提交 5 次”。保持已有布局，避免本次重建地图视觉设计。

## 8. 日期统一

正式游戏以 `DayFlowController` 的逻辑日序作为每日交付的日期来源。利用现有 BeginNewDayFlow -> Actions.BeginDay 接口，保证每天初始化只执行一次。

当前 NCS 也有 world.calendar 和 EndTurn 推进规则。实施时检查正式桥接：同一天的变化只能推进一次，不得由交付完成调用 EndTurn 再偷偷加一天。若正式内容需要 NCS 日期事件，桥接同一个正式日期；不要顺手重写整个日程/数值系统。

载入时先还原 DayFlow、NCS、行动和物品，再按正式日期刷新连续进度，最后开放输入和结局检查。游戏启动或旧档没有完成还原时，不用默认第 1 天提前检查或清进度。

## 9. 变化通知与结局检查

不需要每帧轮询，也不需要大型事件总线。对外提供一次操作处理完成后的轻量通知即可。

以下变化会要求重新检查结局：bool、物品、行动有效进度/完成、被结局引用的 Bar/事件记录，以及新会话/读档完成。换天清除连续进度同样算变化。相同值不重复通知。

一次操作的顺序：先检查 -> 扣费/改数据 -> 处理该操作既定的 NCS 结果 -> 到安全边界 -> 检查结局。不要在逐条 Result、逐种物品扣除、迁移某一字段或 UI Refresh 内触发 GameOver。

具体边界要求：

- 单独 NCS 事件：事件和选项结果执行完，额外已请求演出处理完，再允许结局转换。
- 交付/其他行动：该次行动既定的节点事件和结果事件处理完，再判断；不能在扣第一种物品时结束，也不能在一个行动的第一个结果事件后丢掉后面的既定结果。
- 期间的变化可以只标记“需要重查”；在上述边界检查最新状态，不提前锁定一个可能已失效的候选结局。
- 结局正式选定后，阻止新的行动、下一日和后续自动触发事件继续改变世界；失效回调不能继续推进。不得通过永久等待 IsBusy 清零造成永远不判结局。
- 保存禁止捕获扣费/结果的中间状态；允许保存等待演出中的已完整提交状态，但要连同 pending 事件/节点记录保存。

本版只存必要 bool 和节点记录，不建立所有条件变化的永久历史数据库。

## 10. GameOver 与游戏流程

### 10.1 结局配置

增加最小 `Ending` sheet：endingId、enabled、priority、titleText、messageText。条件放在现有 Condition sheet，ownerType=ending，ownerId=endingId。

本版所有 Ending 都是终局，不增加 NPC 支线结局、阶段结果或多结局演出机制。没有有效启用结局时，游戏照常运行。

多个结局同时满足：priority 数值高者优先，相同按 endingId 的 Ordinal 顺序选择，结果稳定。一个会话最多选中一个；重复通知只返回已有结果，不重复开面板。

测试结局默认 disabled 或要求专用初始 false 条件；不向现有正式内容添加开局即可命中的默认结局。

### 10.2 状态职责

条件查询只返回判定结果，不直接打开面板。结局判断把选中的 endingId 交给 GameFlow，由流程转换处理。

使用已安装 YokiFrame FsmKit 建立最小会话状态入口：Menu、Loading、Playing、GameOver。沿用现有加载/菜单方法；Paused 保留现有暂停处理，只允许在 Playing 内暂停/恢复。本次不把所有 DayFlow 阶段重新实现为另一套状态机。

GameFlow 的公共输入允许、继续、暂停、读档、新游戏、自动存档和日程启动必须统一服从会话状态，不能留下一个并列 gameOver bool 让各处自行猜测。迁移期旧 gameplay 字段可作为状态派生兼容值，不允许两个入口独立决定是否继续游戏。

进入 GameOver 必须：

1. 标记会话结束和选中的结局；只进入一次。
2. 停止 DayFlow 自动推进、地图行动和经营输入/计时。
3. 关闭或挂起可继续游戏的面板与 NCS 调度；使旧协程/回调失效，避免关闭面板后继续执行。
4. 停止自动存档定时器及已经排队但尚未执行的自动存档，防止旧异步任务覆盖可继续测试的存档。
5. 显示标题、正文和“返回主菜单”按钮。复用现有 ResultPanel 外观或增加极小 GameOverPanel 均可，但语义必须由 GameOver 状态控制。

Time.timeScale=0 可以辅助停止经营计时，但不能作为唯一禁止操作手段；未缩放时间的演出和旧回调仍要正确停止/失效。面板按钮和过渡须在暂停时可用。

Esc、关闭通用结果框或暂停菜单“继续”都不能回到 Playing。关闭结束面板只允许返回主菜单。新游戏重置整个会话；主动载入结局前的存档可以开始一个恢复的会话。

选中结局信息放进版本化叙事快照，显式读到已结束快照时恢复 GameOver，不能把它当 Playing。第一版不要求进入 GameOver 自动写档；保留先前自动档，方便继续测试。

## 11. 旧代码简化与配置迁移

范围是简化条件机制及其引用，不是删除整个 NCS。

保留：现有事件/选项/演出、Bar、日期调度、普通行动类型、物品栏、内部防重复/锁定记录、现用人物详情显示状态。

移除/替换：旧复杂条件求值、重复解析/无用字段、旁路剧情 Flag 来源、双份专精、废弃类型分支和仅验证废弃行为的测试。

先列出 Condition、Action.requirements、Result 和专精引用的实际使用情况，再迁移。当前生成内容使用了 Bar 比较、事件发生记录和剧情 Flag，不能简单删除所有条件行。只保留上面列出的简单只读能力，不为了旧测试保留概率/复杂上下文标准。

具体迁移要求：

- 普通 FLAG_SET / FLAG_CLEAR 改成 BOOL_EQ 相应预期值，并给剧情 key 添加定义。
- 旧 Action Cond / NotCond / Bar 检查迁入统一 Condition ownerType=action；Item / ActionPoint 留作消耗。必要过渡解析必须有限、明确，不能永久存在两套判断器。
- 事件已发生的语义保留为只读事件记录，内部 once 标记不开放修改。
- 旧 Switch / ObjectState 先查实际调用。人物详情使用的可见性/解锁值可以继续由其展示状态负责，不扩展成公开多状态条件池，也不能盲删造成 UI 不可用。
- 现有 groupIndex 逐行保留语义，不猜测策划意图或顺手重写剧情分支。
- 专精 ID 统一映射到公开 bool key，详情显示只读新池。
- Validator 和 Loader 与运行时同步改；未知类型、未知引用、非法数量、死亡清除、空结局条件要有可定位报告。

源 Excel、schema、生成 C# 和 JSON 必须一致。测试样例也放入同一配置流程，不建立第二份手写 JSON 标准。

## 12. 自动存档与可继续测试

目标是现有自动档尽量可继续，并保证新版本的完整往返；不承诺任意历史版本兼容。

实施前定位 Application.persistentDataPath 下实际存档目录，先备份当前自动档及必要文件。不得在勘察、测试或迁移时未经说明删除/覆盖唯一旧档。迁移先在内存成功，之后才能写新格式；保留备份。

叙事 envelope 明确升级新版本，同时接受当前 v1 并进行一次迁移；未知未来版本仍明确拒绝。保留其他参与者数据、场景、日序、经营状态和地图背包数量，不因为条件更新清空整个游戏档。

迁移规则：

- 缺少新条件字段：使用定义初始值，然后导入已识别旧剧情 flag。
- 有新版 bool 值时以新版为准；不能用旧专精列表把新版 false 又改成 true。
- 只有旧数据时，从已识别旧专精列表/旧详情专精 flag 导入；忽略无定义内容时记录一次清晰提示。
- 内部 once、事件记录、NpcLocations、正在播放/排队的事件保持其旧职责。
- 背包已有数量只导入一次，不能和另一份旧数据相加导致翻倍。
- 普通旧行动进度保留。明确迁成每日交付的新行动若没有每日提交记录，初始化该行动的交付进度和节点记录，不猜测曾在哪天扣费；其他游戏进度不受影响。
- 缺少叙事参与者的旧档可初始化新的叙事会话，但照常恢复其余参与者。
- 新快照保存 bool、交付最后提交日/进度/节点/完成状态、待执行事件和已结束信息，读档后不开新条件池覆盖恢复结果。

如果唯一旧自动档实际损坏或无法安全迁移：保留原档与备份，明确说明原因，允许正常“新游戏”继续测试；不能反复循环报错或悄悄当作已恢复。用户接受这种有限兼容，不接受无法进游戏的状态。

当前 enableNarrative / ModuleEnabled 存在关闭入口。正式进入游戏时确保唯一条件/行动运行时被正确初始化并参与保存；不能只为人物详情创建临时运行时，导致条件检查可用但自动存档没保存。不要启用重复 HUD、旧 NCS 示例启动流程或自动推进演示事件。

## 14. 验收清单

### 14.1 有意义的逻辑测试

| 案例 | 必须观察到的结果 |
|---|---|
| 已定义 bool 未设置、设置、清除 | 初始值正确；相同值无重复通知；普通 clear 后为 false |
| 死亡设 true，再由普通结果清除 | 清除被拒绝；新游戏/读旧档还原不受误拦截 |
| 拼错 key，并要求它为 false | 配置报错，不能当作满足 |
| 两个同组条件 / 两个不同组条件 | AND / OR 正确，物品只读检查不消耗 |
| 事件及选项合计移除超过库存、先增后减 | 按最终执行顺序预检；不足时 bool/物品不部分提交，不假装完成 |
| 移除专精并重新打开人物详情 | 徽章消失，不被旧 profile 重新补回 |
| 同种钥匙两把 / 不同钥匙各一把 | 同种数量堆叠，不同 ID 分开；UI 和查询一致 |
| 一项物品不足或行动点不足 | 所有物品和行动点不变，进度不变 |
| 同一物品重复成本行合计超过库存 | 整次拒绝，不出现逐行超支 |
| 成功交付后连点、关闭重开、当日读档 | 只扣一次，只加一次，当日禁止再次提交 |
| 库存足够一次交五天 | 当日仍只能提交一次 |
| 累计模式漏一天 | 进度保留；后续继续累计 |
| 连续模式漏一天、跨多天或读档 | 有效进度归零；已消耗资源不返还 |
| 连续中途剧情触发后断档再达到节点 | 进度重算，剧情不重复 |
| 行动完成，之后换天 | 不清完成状态、不再扣费或重发结果 |
| 节点事件演出中保存并恢复 | 恢复待播放内容，不重复扣费/进度/结果 |
| 多条结果先设置 A，再清除 A | 只在最终状态检查结局，不因中间 true 结束 |
| 物品减少、行动完成、Bar 变化触发结局 | 对应来源都能触发重查，不仅 bool 变化有效 |
| 两个结局同时满足、重复通知 | 稳定选择一个，只打开一次面板 |
| GameOver 后旧回调、Esc、暂停继续 | 不恢复经营、不推进下一天、不继续扣费 |
| GameOver 前已经排队自动存档 | 结束后不执行写入，不覆盖此前可继续档 |
| 已结束快照恢复 / 新游戏 | 前者进入结束状态，后者清干净开始新会话 |

### 14.2 Unity 与实际测试

- Unity 编译无错误；Luban 生成成功；新配置校验通过。
- 使用现有 Narrative、Action、SaveBridge 测试位置增加必要测试；废弃类型测试改为验证其配置不再被接受，不用删除断言来掩盖错误。
- 相关既有 NCS 事件/选项、正式 DayFlow、地图行动/物品栏、人物详情、存档回归通过。
- 主菜单新游戏 -> 正式经营 -> 地图行动 -> 下一天可走通；实际进入第二天验证一次累计和一次连续案例。
