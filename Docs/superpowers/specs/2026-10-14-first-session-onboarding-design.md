# 新游戏首日与地图引导 Spec

日期：2026-10-14。状态：设计已获用户确认，待用户审阅本文；本文只定义需求，不包含实现计划或代码修改。

## 1. 目标

补齐新玩家从主菜单开始新游戏，到第一次进入咖啡馆的场外引导。第一天跳过日期切换动画，玩家完成叔叔来信后直接进入地图，并由地图引导进入咖啡馆教程。从第二天开始，沿用现有每日流程和日期动画。

## 2. 已确认决定

- 玩家属性、出身、专精和起始资金继续由信件中的选择决定；不增加独立属性页面。
- 确认信件时使用现有 `PlayerRuntime` / `PlayerSessionCoordinator` 初始化玩家数据，必须一次性提交。
- 头像继续使用配置中的默认头像，不增加头像选择步骤。
- 新游戏第一天不播放 `DateChangePanel`；信件结束后直接到地图。
- 第一天地图聚焦咖啡馆，其他地点在教程入口前不可进入；玩家点击咖啡馆后才开始咖啡馆内的引导。
- 第二天及以后保留日期动画。
- 报纸是有事件时才播放的条件通知，不新增必播报纸演出。
- 咖啡馆模拟教程按《文案-新手教程.docx》执行，详见配套 spec `2026-10-14-cafe-tutorial-ncs-integration-design.md`。

## 3. 玩家流程

```text
主菜单「开始游戏」
  -> 互动信封与信件
  -> 玩家确认署名，按选择提交玩家运行时数据
  -> 自动选用默认头像
  -> 初始化第一天日期与当天必要的游戏状态，不播放日期切换动画
  -> 直接显示城区地图，聚焦咖啡馆
  -> 玩家点击咖啡馆
  -> 进入 CoffeeShop，启动咖啡馆内新手引导
```

第二天从既有日程入口进入：

```text
新一天状态初始化 -> DateChangePanel -> 有事件时按现有规则显示通知 -> 城区地图
```

第一天跳过的是**日期演出**，不是把第一天日期错误地留在上一天，也不是跳过建角、NCS 日序同步或行动点初始化。第一天日期沿用现有配置与日序规则。

## 4. 范围与边界

- 新游戏入口仍由 `GameFlowBootstrap` 管理；信件仍使用现有 `FirstDayLetterPanel` 和草稿提交入口。
- 使用现有 DayFlow、地图场景转换和咖啡馆入口，不新建平行主循环或临时场景。
- 仅改变首次新局首日的演出分支。第二天起、日结、存档恢复及其他既有阶段不应因该分支改变行为。
- 地图点击咖啡馆后进入配套咖啡馆教程；教程的叙事/玩法职责和步骤握手由配套 spec 定义。
- 地图按钮样式、镜头聚焦表现等细节沿用地图已有设计；本 spec 不要求重做地图 UI。
- 第一天发生条件通知时，按现有事件通知规则处理；不得无条件插入报纸面板。

## 5. 存档、重试与防重复

- 信件选择只提交一次。信件动画重播、重复点击署名、场景重载和存档恢复都不能重复发放属性、专精或资金。
- 信件阶段的存档恢复仍恢复信件/建角阶段，不得误播第一天日期动画或跳过尚未完成的建角。
- 玩家已完成建角、但尚未点击咖啡馆时恢复存档，应回到第一天地图引导；不再显示信件，也不重复初始化玩家数据。
- 进入咖啡馆后由配套教程 spec 规定教程阶段的保存、取消和重试行为；它不得导致重新提交建角奖励。
- 已开始游戏的旧存档须按已保存 DayFlow 阶段恢复；不得仅因当前日序为第一天而重新套用新游戏入口。

## 6. 验收标准

- 从主菜单开始新游戏：显示信件；完成信件后直接进入地图，不出现 `DateChangePanel`。
- 信件选项在 `PlayerRuntime`、NCS 属性来源、专精及咖啡馆资金中的结果与既有建角规则一致，只提交一次。
- 信件完成后默认头像已设置，无头像选择面板。
- 第一天地图显示咖啡馆引导；其他地点不能绕过咖啡馆教程入口。
- 点击咖啡馆会进入现有咖啡馆场景并启动配套教程，不重开会话、不重置玩家状态。
- 完成第一天并开始第二天时，日期动画正常播放；后续日序不受影响。
- 当天没有事件时不显示报纸通知；有事件时保留现有条件触发行为。
- 存档恢复和重复回调不会重复创建玩家、发放奖励或丢失当前阶段。

## 7. 验证范围

- 更新现有信件到 DayFlow 的 PlayMode 回归：新局首日应断言地图先于日期演出。
- 覆盖第二天日期演出仍播放、默认头像、建角提交幂等、首日地图入口及存档阶段恢复。
- 地图和咖啡馆切换应使用正式场景及现有场景转换；不另建临时主循环或测试场景。
- 实施前检查当前工作区和正在进行的 DayFlow 修改，保留其他开发者的未提交改动。

## 8. 实施结果记录要求

交付实现时，必须在实现结果/验证记录中写明：

- 实际修改的代码、配置、场景和测试文件。
- 首日与第二日起始流程的实际表现，以及是否与本 spec 一致。
- 执行过的测试名称、结果和未能执行的测试及原因。
- 存档恢复、重复回调和属性/资金幂等验证结果。
- 尚未完成的事项、已知风险和需要叙事/玩法负责人决定的问题。

不得只写“已完成”；结果应能让未参与实现的人按记录复核。
