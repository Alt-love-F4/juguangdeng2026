# 玩家运行时、建角配置与 NCS 数值接入 Spec

日期：2026-10-13。用途：交给开发 agent 实现。本轮只新增设计文档，不修改游戏代码、Excel、场景或存档。

## 1. 目标与确认决定

把为详情面板临时创建的 PlayerDetailsProfile 替换为正式玩家运行时入口，补充玩家与建角配置；让 NCS 查询其他系统拥有的逻辑数值、接收变化通知，使用既有规则判断剧情。

用户已确认：

- 玩家运行时保存自身身份，提供其他系统数据的查询入口，以后按玩法需要扩展。
- 玩家与咖啡馆共用一套资金，由经营系统保存、修改。
- 剧情修改其他系统的数据，通过该系统的业务方法执行。
- NCS Bar 是逻辑数值，不是 UI 控件；数值可以来自 NCS 或其他系统。
- 新游戏检查初始条件；读档恢复不算数值增长，不能凭恢复再次触发跨阈值剧情。
- 必须替换旧 Profile；替换后详情面板仍正常打开，显示正确数据。
- 本对话只确定 spec；工程实现由其他 agent 执行。

下面将这些决定落成可执行规则。具体初始金额属于可调测试默认值，不是用户已确认的游戏平衡结论。

## 3. 玩家运行时的边界

推荐命名 `PlayerRuntime`；自身可序列化数据为 `PlayerState`。两者是普通 C# 对象，由当前游戏会话持有；Unity 适配层绑定现有系统和资源。具体命名可调整，职责必须保持。

| 数据 | 唯一保存位置 | 玩家入口用途 |
|---|---|---|
| 固定 playerId、姓名、头像选择、是否已选头像 | PlayerState | 读取身份，执行经过校验的身份修改 |
| 出身 ID、建角选项 ID、是否已提交建角 | PlayerState | 生成背景介绍，阻止重复发建角奖励 |
| 语言、勇气、智慧、知觉 | NCS 内部 Bar | 按属性 ID 查询，修改走 NCS 数值入口 |
| 专精 | 已有条件池 | 按专精对应条件 key 查询、修改 |
| 行动点和上限 | 已有行动点对象 | 查询；消耗、恢复、上限变化走行动系统 |
| 个人物品和数量 | 已有地图背包 | 查询；增减走同一个背包入口 |
| 共用资金 | CafeWorld | 查询；增减走经营系统入口 |
| NPC 关系 | NCS 关系状态 | 使用已有 ID 和关系模型查询 |
| 日期、阶段、任务进度、剧情触发记录 | 原所属系统 | 按需要查询，不复制到玩家状态 |

第一版至少提供身份、四项属性、专精、行动点、物品数量和共用资金查询。未知 ID、系统未就绪与合法 0/false 必须区分，不能假造默认结果。可使用 TryRead 类接口或显式状态结果。

不暴露可任意写入的属性数组、专精列表、背包字典。以后新增字段时确定所有者、修改方法、通知和存档规则；不预造任意类型的全局数据袋。

背景介绍由建角 ID 和 Text 模板生成，不承担剧情判断。旧档无法还原选项时可保留 legacyBackgroundText 供展示，不从中文简介猜玩法状态。头像资源继续引用现有 Object/展示配置，存档只记选择，不存 Sprite。

## 4. 玩家与建角配表

新增 `Assets/ConfigTables/Data/Player/Player.xlsx`，走现有 Luban strict 管线。正式运行读取生成数据，文本在 `Shared/Text.xlsx`。实际创建、填表和生成由开发 agent 执行。

采用以下五个 sheet：

| Sheet | 字段及含义 |
|---|---|
| PlayerConfig | playerId（引用 Object）、defaultAvatar、defaultOriginId、baseStartingMoney、actionPointMax |
| PlayerAttribute | attributeId、barKey、nameText、descriptionText、seq；只映射展示，不重复定义初始值和上下限 |
| CreationGroup | groupId、seq、required；第一版为出身、性情、往事、专业、特点五组 |
| CreationOption | optionId、groupId、seq、labelText、descriptionText、originId（可空）、startingMoney（-1 表示不覆盖基础资金）、specializationConditionKey（可空） |
| CreationBonus | optionId、attributeId、delta；同一 optionId＋attributeId 唯一 |

沿用当前五组选项和效果，迁入表中：

| 组 | 选项及效果 |
|---|---|
| 出身 | 贫寒→流浪儿；平民→平民；富贵→贵族。分别设置不同初始资金 |
| 性情 | 善良：语言＋2；赤诚：知觉＋2 |
| 往事 | 勇敢：勇气＋2；明睿：智慧＋2 |
| 专业 | 神学：宗教专精、知觉＋2、语言＋1；文学：文学专精、语言＋2、勇气＋1；数学与物理科学：科学专精、智慧＋2、知觉＋1；历史与官房学：政治专精、勇气＋2、智慧＋1 |
| 特点 | 能言善辩／坚定无畏／聪颖睿智／敏锐细腻：分别对应语言／勇气／智慧／知觉＋2 |

第一版 groupId 固定为 origin、temperament、memory、education、trait，五组均 required=true。出身 originId 使用 waif／commoner／noble，分别对应流浪儿／平民／贵族；迁移映射沿用这三个稳定 ID。PlayerConfig 的默认行：playerId=player、defaultAvatar=Male、defaultOriginId=commoner。optionId 采用组名加稳定语义名称，不使用行号；标签与信件填词引用 Text，效果说明由同一配表生成，避免文字宣称与实际奖励不同。

四项属性 key 为 `player.language`、`player.courage`、`player.wisdom`、`player.perception`。初始值、范围只定义在 NCS Bar：第一版初始值 0、范围 0～20。PlayerAttribute 只引用，不定义第二套初始属性。

专精复用条件 spec 的 key，例如 `specialization.player.letter.religion`。已有 key 保持稳定，不能靠重命名 key 清除旧档状态。

可调测试默认值：baseStartingMoney=500；三种出身资金为 250／500／1000；actionPointMax=5。现有跳过开场路径采用平民出身、基础资金、基础属性、无专业专精和现有默认头像，姓名引用 player 的既有名称文本；不新增跳过入口。

baseStartingMoney 是正式新局的资金初始化来源。CafeCatalog.startingMoney 可继续供独立经营测试使用，正式初始化后不能再次覆盖资金。出身金额是最终起始余额，不是加在基础余额上的奖励。

姓名沿用当前规则：去首尾空白、过滤控制符和富文本标签字符、最多 16 个现有输入单位；提交要求有效非空。本轮不改字符计数方式。

校验至少覆盖：重复 ID/组内排序、缺失必选组、未知属性/Bar/条件/Text 引用、playerId 非 player、负上限、非法金额、重复属性奖励、产生多个出身或资金覆盖的歧义。第一版只有出身组定义出身及金额，只有专业组定义专业专精；三种出身按贫寒＜平民＜富贵校验。

新局使用当前表值；已建角存档保留实际属性、资金和专精，读档不重算奖励。未提交草稿按当前表展示；optionId 被删除时明确要求重选，不静默换选项。

## 5. 草稿和一次性建角提交

FirstDayLetterDraft 继续只管理草稿，效果改读配表。Panel 编辑草稿并发确认，不直接修改玩家、NCS 或经营存档。信件组和选项按稳定 ID 绑定，不靠显示顺序当永久身份。

会话协调入口执行：校验草稿和所有依赖→计算完整结果→在输入及剧情检查关闭的初始化阶段提交身份、属性、专精、起始资金→标记建角已完成→开放初始条件检查。先应用完整结果，再检查剧情。

必须满足：

- NCS、条件池、经营资金所有者就绪后才提交；等待时不发部分奖励、不提前标记完成。
- 连点、重复回调、关闭重开、重播、读档不能重复加属性、加钱或授予专精。
- 正式提交后不使用“减去旧奖励再加新奖励”修改已开始游戏的人物；重播只展示。本版不增加洗点或重新建角。
- 中途存档保存姓名及已选 optionId 草稿。恢复已完成建角的存档只恢复结果，不再执行初始化。
- 提交前预检确定性错误；初始化异常停留在可重试的未提交状态，不留下可继续游戏的半个人物。
- 重开场景或面板不创建第二个玩家会话；返回主菜单结束会话，再开新局获得全新状态。

## 6. NCS 数值目录和统一查询

保留 Bar 身份、范围、Trigger 及关系语义，扩展数据来源：

| 定义 | 保存与查询 |
|---|---|
| sourceMode=ncs | NCS 保存当前值，沿用 BAR_ADD/BAR_SET、边界约束和存档 |
| sourceMode=external | 按 providerId＋sourceKey 查询所有者；不往内部 bars 复制可写值 |
| advanceMode=derived | 沿用加权求和，经统一查询读取内部/外部依赖，不独立保存结果 |

新增 `sourceMode`、`providerId`、`sourceKey`；旧定义缺省 sourceMode=ncs。derived 仍使用既有 advanceMode，要求 sourceMode=ncs、外部字段为空，表示 NCS 求值而非保存派生结果。external 不允许 derived 或自动 monotonic 推进。

同一 barKey 在一个会话中只有一种来源；重复注册、运行中静默换来源、未知 provider 回退内部存储均报错。不同单位或业务概念使用不同 ID。第一版不配置多个 Bar 直接映射同一业务事实。

首批真实适配：

| providerId／sourceKey | 建议 Bar key | 真实所有者 |
|---|---|---|
| cafe／money | cafe.money | CafeWorld 实际共用余额 |
| actions／current | player.action_points | 现有行动点 Current |
| actions／max | player.action_points_max | 现有行动点 Max |
| dayflow／day | world.calendar | 正式 DayFlow 逻辑日序 |

物品继续使用已有 ITEM 查询和背包通知，不自动给每件物品新建 Bar。

正式 world.calendar 查询同一个 DayFlow 日序。既有正式日期同步/调度入口保留必要的“当天是否已处理”记录，不能维护可独立加天的第二套正式日期。正式 ADVANCE_DAY/EndTurn 遵循已有 DayFlow 约束，不借数值修改另加一天。本轮不重写日程状态机。独立 NCS 测试如需内部日历，采用明确测试配置，不作为正式来源缺失的回退。

原 state.TryGetBar、条件、派生、详情、Trigger 都接统一数值解析入口；不能只有新接口支持外部值而旧条件仍只读内部字典。

沿用 int 数值体系，资金使用实际整数单位，不压缩成 0～20。外部 Bar 范围描述真实可读范围，读取时不为 UI 截断业务值。 第一版资金和行动点目录范围为 0～int.MaxValue，正式日序沿用现有 1～9999 的配置范围；UI 若要展示行动点占比，使用行动系统的实际 Max，不把目录上界当每日点数上限。派生沿用原舍入/范围规则，校验循环与未知依赖，使用足够宽的中间数避免溢出。外部 provider 变化要重算受影响派生值。

## 7. 变化通知和阈值判断

适配器提供读取、就绪状态、订阅/取消订阅。变化能确定数值 ID、旧值、新值及所属会话/操作；操作标识可复用现有机制，不要求新建通用事件总线。

NCS 可保存上次观测值用于比较，但它是缓存，不能写回所有者，也不能作为第二份外部事实从存档恢复。

| 情形 | 规则 |
|---|---|
| 900→1100，阈值 1000 | 沿用 up/cross 检查 |
| 1100→900 | 沿用 down/cross 检查 |
| 1100→1100 重复通知 | 无变化，不重复产生 crossing |
| 同次操作 900→1100→900 | 比较结算前后 900→900，不触发中间态 crossing |
| 两次独立结算先跨上再跨下 | 分别处理，不能按同一帧合并丢失 |
| 只要求当前达到阈值 | 使用原 hold/条件规则，在规定边界检查 |

一次操作涉及多系统，先完成所有修改，再比较数值、重算派生、检查条件/Trigger/结局并排队剧情。扩展既有 operation/settling 边界，不能仅延后结局却让普通 Trigger 提前执行。派生的旧值来自结算前依赖快照，不能等来源改变后再读取；同操作只比较一次最终派生变化。

演出中仍允许的正常经营变化由所有者提交，NCS 按操作顺序接收并排队；不能因忙而丢通知，也不能在来源回调里递归抢播。暂停遵循已有经营规则。 延迟消费时使用每次已结算操作携带的旧值、新值及必要派生比较结果，不用稍后查到的最新值吞掉中间跨越；事件附加条件在实际调度的安全边界读取完整当前状态，沿用既有排队校验语义。

once、repeat、reachCount、优先级、事件/选项与特效沿用现有 NCS。通知和结果通过队列与结算边界处理；出现无法收敛的循环时中止相关处理，报告事件和 Bar，不无限递归卡死。

## 8. 剧情修改其他系统

外部 Bar 只提供读取。BAR_ADD/BAR_SET 指向 external/derived 时必须拒绝，报告 resultId 和 barKey，不写反射字段或缓存。

补齐 `MONEY_ADD` / `MONEY_REMOVE` Result，target 为共用钱包标识 `cafe`，value 为正整数；调用 CafeWorld 资金业务入口。金额不足或溢出时失败，不静默扣到 0、不部分扣款。已有经营罚款规则不借此全局重写，新剧情扣款使用严格规则。

物品复用 ITEM_ADD/ITEM_REMOVE；属性用内部 BAR_ADD/BAR_SET；专精用条件池 SET_FLAG/CLEAR_FLAG；行动点沿用行动系统消耗入口，本版不新增任意点数编辑脚本。

对同一事件及所选选项的条件、物品、资金结果，按 seq 在临时值预检，包含先加后减、重复扣除和溢出；预检通过才提交这批结果。失败不部分修改、不标记事件正常完成，留下可定位错误。其他 Result 保持原业务边界，不建设任意跨场景事务引擎。

建角起始资金由初始化入口设最终余额且只执行一次；剧情奖励调用加钱入口。把起始余额当奖励反复累加属于错误。

## 9. 新游戏、还原和运行保护

### 9.1 新游戏

创建会话→加载校验配置→创建所有者和适配器→应用已确认建角或既有跳过路径默认结果→建立真实数值基线→在安全边界检查初始条件及 hold→开放输入和后续变化调度。

cross 表示真实运行中的跨越，新游戏不伪造 0→初始值。建角未完成时，不用临时默认属性、资金提前触发正式初始剧情。

### 9.2 读档

进入还原阶段并关闭输入、数值触发、自动保存→验证快照和迁移数据→还原身份、CafeWorld、NCS 内部值/条件/触发记录、行动点/背包/交付、DayFlow→绑定当前所有者→建立实际值基线，刷新派生及日期进度→恢复原排队演出与调度→安全边界检查当前条件和结局→开放输入及自动保存。

还原中的 0→存档值、默认值→存档值、行动点 ResetForDay→当前值均非玩法变化。通知由同一还原屏障抑制或标记还原来源；不能仅关闭 UI 或暂停结局检查。

恢复后 hold 按已有次数记录检查，不执行伪 crossing，不重发已提交 Result。待播放事件和 once 记录直接恢复，不靠再次变化重新猜测。合法恢复为 GameOver 时沿用已有结束流程。

### 9.3 缺失、重绑定和保存

- 未知 key、未定义属性、缺失 provider、未就绪与合法 0 分开。配置错误报错；临时未就绪关闭依赖操作和检查，显示加载/不可用，不用默认值骗过条件。
- 重绑定先取消旧订阅，旧会话回调按会话身份丢弃；同局场景重载保留真实状态，重建基线不产生 crossing。
- 初始基线前不开放玩法。运行中必要来源失效时阻止依赖结算、报告故障，不能修改后靠重绑定抹去变化；正常绑定完成后才恢复。
- 未变化不重复通知，成功变化必须有真实通知，不等详情打开才发现；不逐帧扫描全目录，既有 Changed 可由适配器比较相关字段。
- 只在稳定结算边界抓取存档；初始化、还原、建角提交、结果结算、未处理的数值变化期间拒绝或延后保存。自动保存恢复执行前重查会话仍有效，不能保存半次扣费。
- 坏档、必要配置缺失、迁移失败不覆盖原档、不进入半恢复状态；保留/恢复当前有效会话或回主菜单明确显示失败。
- 运算、范围或业务规则失败必须返回明确结果，不宽泛 catch 后继续推进剧情。

## 10. 存档迁移和旧 Profile 退出

新增版本化玩家参与者，例如 `game.player-state.v2`，保存身份、建角完成标记、尚未提交草稿。外部数据各由所有者保存；NCS 保存内部 Bar、条件、触发次数/事件记录及原待处理剧情。订阅、缓存、派生结果不作为独立事实保存。

旧 `game.player-details-profile.v1` 一次性迁移：

1. 导入姓名、头像和选择标记、已知出身，保留必要旧背景展示文本。
2. 原快照已有 NCS 属性时以它为准；原快照确实缺失时才将旧 Profile 对应属性一次性导入 NCS。不能先生成默认 Bar=0 再误判“已有数据”。
3. 专精沿用条件 spec：新条件快照存在时以 true/false 为准，旧列表不能补回已移除专精。
4. CafeWorld 余额和行动快照的点数/背包优先；读档不重发起始钱、不恢复每日满点、不重新套建角加成。
5. 已进入正式玩法的旧档视为建角已提交；明确开场未提交状态才恢复草稿，不能因旧标记缺失重复领奖。
6. 已知旧出身中文用固定迁移映射；无法识别保留 legacy/unknown 并报告，不猜成有玩法效果的出身。

新旧玩家参与者并存时新版本优先，旧数据只用于诊断，不合并发奖。新存档只写新结构；旧数组、列表、letterBonuses 退出运行时。旧类可仅作为迁移 DTO 保留，正式调用、详情、信件提交和保存注册全部转向新入口。

沿用条件 spec 的当前自动档兼容目标，在备份副本验证；不要求支持全部历史开发坏档。无法兼容报告实际原因，不删除自动档来证明继续游戏可用。

## 11. 详情面板兼容要求

保留 DetailsPanelData 快照、IDetailsPanel 显示接口及三页布局。DetailsGameDataAdapter 改读正式玩家入口和统一数值查询；Panel 只显示快照，不查全局状态或结算奖励。

- 正式详情按钮和调试入口正常打开；我的信息、人物关系、世界情况切页、关闭重开、缓存生命周期不退化。
- 姓名、头像、背景、四属性、专精来自唯一来源；移除专精后重开不复活，属性变化不回退旧数组。
- 关系和世界 Bar 也支持统一查询；可见性、排序、原上下限说明沿用现有规则。
- 打开时按原数据源通知刷新；关闭取消订阅，重开读新快照，防止重复监听和跨会话残留。
- 未就绪有明确状态或沿用加载屏障；缺四项正式属性是配置错误，不静默补临时 Profile 数值。
- 共享调试场景用快照/隔离数据源，不启动正式会话、推进日期或写档；占位显示作为调试能力保留，不成为正式回退。

本轮不因数据替换重建详情 Prefab 或改布局。

## 12. 验收

### 12.1 逻辑与存档

| 案例 | 必须观察到的结果 |
|---|---|
| 三种出身开新局 | 起始资金来自表，属性/专精正确，玩家、经营 HUD、NCS 余额一致 |
| 建角连点、重播、恢复已完成开场 | 仅提交一次，资金/属性不重复累加 |
| 草稿改选再确认、中途保存读档 | 只应用最终选择，恢复后能继续选择 |
| 无效选项/条件/Bar、依赖未就绪 | 错误可定位，不提交半份人物 |
| 内部属性经剧情变化 | 玩家、详情、条件读数一致，旧数组不参与 |
| 资金 900→1100，阈值 1000 | 真实经营变化触发，重复通知不重复 crossing |
| 跨上、跨下、重复跨越 | 按原方向、once/repeat/计数执行 |
| 同次过阈值再回原值、两次独立结算 | 前者忽略中间态，后者两次均被处理 |
| 外部值参与派生或存在循环 | 正确比较最终派生变化；循环校验拒绝 |
| 剧情加钱、先加后扣、超余额、溢出 | 走经营入口；非法整批不部分提交、不标记完成 |
| BAR_SET 指向外部资金 | 校验/执行拒绝，余额不变 |
| 未知 key、来源缺失、余额为 0 | 可区分，缺失不当低值触发 |
| 初始余额满足 hold、超过 cross 阈值 | hold 按规则检查，不伪造 crossing |
| 恢复 1100 元、当天剩 2 点 | 不重触发 crossing、不发起始钱、仍剩 2 点 |
| 待播放剧情保存恢复 | 恢复队列，不重扣费、不重发结果 |
| 同日重复初始化、换天、读档跨日 | 日序只推进一次，点数/交付按既有规则刷新 |
| 旧档两份属性冲突、专精已清除 | NCS/新条件优先，不补回旧值或专精 |
| 结算中自动保存、加载失败 | 不产生半次结算档，不覆盖原档、不继续半恢复 |
| 回主菜单再新局、多次绑定场景 | 无旧数据/回调残留，一次变化只处理一次 |

使用既有 Narrative、Action、SaveBridge、详情测试位置，针对真实语义补例，无需为普通 getter 写镜像实现测试。
