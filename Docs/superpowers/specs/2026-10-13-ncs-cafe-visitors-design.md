# NCS 驱动咖啡馆特殊顾客来访 Spec

日期：2026-10-13。状态：玩法已讨论确认，本文为工程交接稿，供用户审阅后交给 Locus 实现。

职责：Codex 负责分析和本文档；Locus 负责工程代码、Excel、Luban 生成及验证。本轮只新增此 Markdown，不修改工程、不运行 Unity、不提交 Git、不启动其他 agent。

## 1. 已确认的玩法

特殊 NPC 是有故事的正常顾客：有订单、占一个普通客流名额、占座位、有耐心。耐心耗尽会走，玩家可以错过这次故事机会。

- 到店前、订单未完成、订单完成后、离店等阶段均可插入 NCS 演出；阶段是否有内容由表决定。
- 普通顾客完成订单直接离店。特殊顾客送餐后是否离店，由配置决定。
- 特殊人物可使用为某张桌子制作的专属素材。当天来访确认后，应在普通客流之前预留对应座位；本次来访结束才释放。
- 未填写到店时间时，开店第一批优先接待特殊人物；已有营业中的即时来访立即申请入座。
- 没有可用座位就等空位，不挤走普通客人。等候阶段不生成订单、不开始耐心倒计时。
- 正式演出期间暂停经营模拟，演出结束后恢复。
- 空配置和可选字段缺省允许运行，但诊断必须说明哪些配置为空、哪些功能未验证，不能把没有剧情算作剧情测试通过。

实现默认值（便于第一版执行，非追加玩法需求）：未配置送餐后行为时按普通顾客送完离店；配了留店时沿用剩余耐心；等位持续到入座、NCS 取消或打烊，不另设等位耐心。点击剧情可重复性仍由 NCS 事件自身决定。

## 2. 现有能力与需要新增的能力

2026-10-13 只读核对的接入点如下；工作区已有其他工程变更，Locus 实施前须重新核对，不能覆盖他人修改。

| 当前入口 | 已有能力 / 限制 |
| --- | --- |
| `NarrativeDefinitions.cs` / `NarrativeController.ApplyResult` | SPAWN_NPC、DESPAWN_NPC 是结果类型；更新 NpcLocations，不是另一个事件 |
| `NarrativeRuntime` / `NarrativeController` | 有 EffectRequested、事件队列和结果结算；咖啡馆完整来访协议尚未接入 |
| `PresentationResources.Npc` | 旧入口直接按角色 ID 加载 Prefab；cafe 必须改由咖啡馆接管，避免重复生成 |
| `CafeWorld.Business.cs` | 普通到店分座位、生成订单和耐心；送餐、超时、自动流程会移除人物，必须统一改造特殊分支 |
| `CafeWorld.People.cs` / `CharacterCatalog` | 已有身份快照与 Object/Text 角色资源解析，不维护另一份人物资料 |
| `FreeCafeRuntime.Update` | 调用 World.Tick；禁止输入不等于暂停模拟，需要显式经营暂停判定 |
| NCS 正式日历接口 | 当前有 SetOfficialDay / ProcessOfficialDay 等新入口，沿用 DayFlow 的正式日历；不能另起咖啡馆日期计数 |

事件执行结果可以改变状态，进而触发后续事件。UnlockEvent 是解锁，PlaySetup 是演出调用；不得把它们解释为通用“调用任意事件”。本功能不新增通用事件嵌套语言。

**只读 NpcLocations 不够。**同一个人可以多次来访；位置变化不能区分一次结果的重复通知和下一次真正来访。需要为来访记录独立 visitInstanceId，并持久化是否已经结束。

## 3. 系统分工与通知契约

```text
NCS：确认来访 / 到场结果 / 取消或离场结果
  → 在安全结算边界发布已提交的来访状态
咖啡馆接入层：同步预留、等候、座位和实体
  → 咖啡馆领域层生成订单并运行耐心
领域层：报告入座、送餐、超时与离店等事实
  → 接入层反馈 NCS，由 NCS 配表安排演出和剧情结算
```

### 3.1 NCS 发给咖啡馆

- 通知发生于整个事件结果及已选选项结果提交之后，不在每一条 ApplyResult 中直接创建场景人物。
- 发布可恢复的来访状态快照，包含新预约、实际到场请求、取消、结束状态和提交版本。
- 快照必须是稳定的只读数据；不能把正在修改的字典直接作为所谓不可变快照传给订阅方。
- 咖啡馆首次绑定、场景加载、组件重新启用时主动拉取；NCS 读档和新会话完成后重新发布。
- NCS 不直接依赖咖啡馆程序集或 Prefab；咖啡馆领域层不依赖 NCS、cfg 或 UI。接入层翻译 DTO。
- 所有订阅有明确 owner，停用/销毁时解除；NCS 尚未就绪时保持待同步，不隐式启动模块。

概念接口职责：获取已提交的来访快照、订阅快照变化、反馈生命周期事实。接口名字和文件拆分由 Locus 按当前工程模式确定。

### 3.2 咖啡馆反馈给 NCS

反馈至少携带 visitInstanceId、characterId、阶段、离店原因、通知序号。NCS 在安全边界接受，忙于演出或结果结算时排队，不重入当前事务。

- 同一阶段事实只接受一次；重复通知、读档重播、自动上餐不能重复结算。
- 玩家点击是可多次产生的独立请求，有序号；不把“点击一次”当作“本阶段永远不能再点击”。
- 反馈不能绕过事件条件、锁、onceOnly、选项和正式演出队列。
- 反馈结束时把本次来访标记为终态，再处理后续剧情；不能靠咖啡馆删除实体、NCS 仍保留 active 来访。
- 清理 cafe 位置前检查它仍归属此来访，旧来访的延迟反馈不能覆盖人物的新地点或下一次来访。

## 4. 来访配置与提前预留

### 4.1 配置结构

建议在现有 Narrative.xlsx 中增加 CafeVisit 与 CafeVisitHook，不在 tags 塞事件 ID，不在 C# 写正式剧情。

CafeVisit（来访预设，一行一个 visitKey）：

| 字段 | 用途 | 缺省 |
| --- | --- | --- |
| visitKey | 稳定预设 ID；不是本次运行实例 ID | 必填 |
| characterId | Object 角色 ID | 必填，必须能查到 |
| preferredSeatId | 指定普通座位 ID | 空：普通空座位分配 |
| seatedVisualPath | 该位置对应的专属人物素材，沿用项目资源路径约定 | 空：Object 室内资源 |
| arrivalDelaySeconds | 营业开始后的延迟秒数，使用可暂停的经营时间 | 空/0：开店第一批；营业中收到 0 请求立即到店 |
| patienceSeconds | 入座后的耐心 | 空：普通顾客默认耐心 |
| leaveAfterServed | 送餐及送餐阶段演出结束后离店 | 空：true；false：留店并继续剩余耐心 |

只依赖 SPAWN_NPC 的 target=obj:角色ID、value=scene:cafe 时，按角色查唯一默认预设；找不到使用普通默认行为并报告缺省。一个角色配置多套预设时必须显式选择，不随机猜测。

CafeVisitHook：visitKey、stage、trigger、seq、eventId。trigger 为 auto 或 click。阶段和触发规则见第 6 节；同一阶段多行按 seq 顺序请求，eventId 是正式 NCS Event ID。

上述表结构为待实现设计，当前工程未声称已具备。Locus 应与现有 schema 约定一致，先改 schema/Excel，再官方 Luban strict 生成，不手改 generated C# / JSON。

### 4.2 提前预约与实际到场必须分开

不能只在 SPAWN_NPC 时才预留，也不能扫描未来 EventDate 并提前执行它的条件或结果。

建议新增咖啡馆专用结果 `RESERVE_CAFE_VISIT`：target=obj:角色ID，value=visit:visitKey。它确认本次来访，创建实例并预留座位/客流额度，但不把人物记录成已经在场。

- 用开店前的 NCS 事件执行预约，DayFlow 必须在普通顾客首批生成前完成预约快照对齐。
- SPAWN_NPC obj:角色ID → scene:cafe 激活同一未结束预约；若无预约则创建立即来访，允许等位。
- 预约记录可携带到店延迟；它已经是 NCS 的来访授权，到点只由咖啡馆落实，不重新判定剧情。
- 到场结果和延迟同时存在时，两个条件均满足后入座：到场授权已提交，经营时间已到；空时间等于立即满足时间条件。
- DESPAWN_NPC 或人物被移动到别处，结束对应预约/等候/在店来访并释放预留。
- 到场反复同步不是新来访。对已在场同一角色的重复 Spawn 合并；结束后需要新的 NCS 结果提交才允许新的实例。

若 Locus 能复用现有明确等价的预约能力，可不新增上述结果名，但必须提供提前预留、实例去重及实际到场分离的证据。不得自行引入另一套剧情调度。

## 5. 座位、等位与客流

- 专属座位仍是普通座位，预约到来访结束之间只属于这次来访。等待到点期间也不分配给普通客人。
- 入座、离座、预留与释放通过咖啡馆的统一座位管理入口；不再只靠 customer_座号 是否存在判断空位。
- 预约尚未入座时预留一个客流额度，真正入座才增加实际特殊顾客到店计数；不因重复同步、等位重试重复计数。
- 生成普通顾客时保留已确认特殊来访的额度，并排除被预留座位。不要把预留引起的满座当作普通顾客“到店失败”反复扣声望。
- 开店首批先安排可以入座的特殊人物，再补普通顾客。普通客流预算和预留数量冲突时保证已确认预约的额度，明确报告最低客流调整，不能静默丢预约。
- 营业中无预约的特殊到场，如果预算已用完，则等候到打烊并报告 budget_unavailable；不能暗增额度或挤掉普通客人。
- 普通客人已经坐在专属座位时不强制赶走：先阻止后续普通客人再次使用，特殊人物等待此座位释放。
- 同一座位被两位特殊人物申请时，按预约提交顺序排队；各自结束后交给下一位。冲突必须显示诊断。
- 没配专属座位时，按等候提交顺序分配普通空位；有等待特殊人物时优先于新的普通顾客。
- 不跨天无限保留未结束预约：打烊结束当天预约/等候/在店来访；第二天重来必须由 NCS 再授权。

素材边界：专属 seatedVisualPath 只有在匹配的专属座位上才使用。座位配置失效退回普通座位时使用普通室内资源，不把专属坐姿硬套到另一张桌子。释放座位后恢复普通桌位视觉。

## 6. 状态、订单与阶段演出

运行状态：Reserved → PendingArrival → WaitingForSeat → SeatedBeforeServe → Served → Ended。没有预约时可以从 PendingArrival 开始；Ended 不再被快照重建。

| 阶段 | 可自动触发 | 可点击触发 | 计时 / 业务 |
| --- | --- | --- | --- |
| reserved / waiting | 支持到场前内容；等待时无场景人物可点击 | 本轮不增加等位 UI 点击 | 无订单、无耐心 |
| arrived | 入座、订单初始化完成后自动演出 | 随后进入 before_served | 每个实例只发生一次 |
| before_served | 如需入座后内容使用 arrived | 未完成订单时点击 | 普通订单与耐心 |
| served | 成功上餐后自动演出 | leaveAfterServed=false 时可点击 | 不再有未完成订单，仍保留人物/座位/剩余耐心 |
| leaving | 所有离店原因均可配置自动演出 | 不再接受新的点击 | 已停止计时，不再接单，等待当前演出收尾 |
| ended | 终态反馈后可安排后续 NCS 事件 | 无 | 释放人物与座位，不再复活 |

- 自动阶段事件配置顺序明确；前一个未结束时后一个排队，不重叠开 Panel。
- 上餐先完成唯一一次订单经济结算，再触发 served 内容；不能为了播放内容复制订单或重复收入。
- leaveAfterServed=true 也必须先给 served 阶段演出机会，演出收尾后再走离店流程，不先删除人物。
- leaveAfterServed=false 使用独立的来访耐心记录保存剩余值；订单从请求列表移除后仍需正确计时。打烊不把已完成订单重复算失败。
- 超时先判定本次机会结束，禁止新的互动；配置的 leaving 内容完成后执行清理。演出期间不能重复触发超时。
- NCS 主动移走人物为强制结束；已经播放的演出按现有取消/完成约定收尾，尚未启动且不再符合阶段的点击不执行。
- 自动阶段无配置时立即继续；条件不满足时正常跳过并显示原因，不能卡住顾客离场。
- 等位人物没有必要生成场景对象；若后续要门口人物展示，另行确认，不影响本轮等待逻辑。

结束原因至少区分 served、patience_expired、ncs_despawn、location_changed、business_closed、reservation_cancelled。取消/等待未入座不算未完成订单；入座后的超时和打烊按正常订单规则结算。该 NPC 故事是否永久错失、后续是否再来，由 NCS 决定。

## 7. 正式演出期间暂停经营

使用统一的经营模拟暂停原因，覆盖现有 Conversation / Reading / Notice / CutScene 及共用演出入口；只屏蔽输入不满足此要求。

- 日内经营时钟、普通与特殊顾客耐心、新客间隔、特殊到店延迟、自动点单/送餐、设备加工等 World.Tick 推进统一暂停。
- 演出本身继续使用现有非缩放时间，不用全局 timeScale=0 搞停演出。
- 多层演出/暂停叠加，只有全部经营暂停原因解除后才继续；取消、关闭、异常、场景卸载均释放 owner。
- 不要求整个 NCS 队列忙时永远冻结：预约和无演出结果提交可以同步完成；真正演出与阶段交接需明确暂停，避免超时抢先发生。

## 8. 存档、同步和结束反馈

- NCS 保存每次来访授权、实例 ID、终态和已接受反馈；咖啡馆保存座位/预留、经营时间、订单、剩余耐心、运行阶段和待交付反馈。
- 同步只按未结束实例补齐。NpcLocations 仍维护人物地点，但不是自动生成的唯一依据。
- 两边恢复完成前不按临时空快照删除人物；建立完成恢复屏障后统一对齐，兼容先恢复哪一方。
- 已结束实例即使旧咖啡馆快照有实体也必须清除；相同角色新的来访不能被旧实例结束通知清掉。
- 等位、延迟到店、订单完成留店、演出交接与待反馈各状态可恢复；不能再次发订单/再次扣客流/再次发奖励。
- 保存时采用现有正式存档流程，保证两边同一逻辑边界。传输中的反馈保存并按 ID 重投，NCS 去重；不建通用消息数据库。
- 取消预约、DESPAWN、超时、打烊、手动/自动送餐都走同一结束入口；不能留下座位锁或一个仍 active 的 NCS 实例。

## 9. 空配置、错误配置与调试

| 情况 | 行为与诊断 |
| --- | --- |
| 整个 CafeVisit / Hook 为空 | 普通经营照常；明确显示“特殊来访配置为空、阶段剧情未配置” |
| Spawn 指向有效角色，但无来访预设 | 生成默认来访：立即/开店优先、普通座位、普通订单/耐心、送餐后离店；一次缺省提示 |
| arrivalDelaySeconds 空 | 0，不能因空字段解析失败 |
| preferredSeatId 空 | 普通座位；满座等位 |
| 专属座位不存在 | 一次警告，回退普通座位和普通室内资源，不抢位、不崩溃 |
| 阶段没有事件 | 显示未配置，正常继续；该阶段演出测试标记未覆盖 |
| 事件 ID 不存在 | 警告并跳过；释放交接锁，不阻塞营业 |
| 事件条件不满足 / 已锁 / onceOnly 已完成 | 正常拒绝，记录明确原因；不伪造已播放结果 |
| 负数/非法时间或耐心 | 警告，时间回退 0、耐心回退普通默认值 |
| 人物不存在/无有效世界资源 | 不创建假角色；拒绝该实例、结束并反馈 configuration_invalid，释放预留，诊断错误 |
| 专属素材路径坏但普通资源有效 | 警告，使用普通资源；不能声称专属素材已验证 |
| 座位重复预约/同人重复到场 | 诊断并排队/合并；不得复制人物或默默挤客人 |

调试至少展示：实例 ID、角色、配置是否缺省、状态、预约座位、实际座位、客流预留、延迟剩余、耐心剩余、当前阶段事件、结束原因、反馈是否已提交。使用已有 GM/调试能力；不把工程诊断塞进正式产品流程。

日志按实例/错误键去重，不能每帧刷警告。缺省、无内容、条件拒绝、配置错误四种情况分别标注。

## 10. Locus 需要制作的最小示例

在真实 Excel 中新增一位已有有效资源的特殊人物来访示例；优先查 Object 中已有角色，确实缺失才补身份，不能覆盖现有正式人物资料。

- 到店前事件：预约 visitKey=demo_cafe_visit，预留一个实际存在的普通座位。
- 到场事件：SPAWN_NPC，target=obj:实际角色ID，value=scene:cafe；到店时间留空，验证开店首批优先。
- before_served 点击事件：一段明确标为示例的 Conversation。
- served 自动和点击内容：至少一段；配置 leaveAfterServed=false，验证完成订单后仍可聊。
- leaving / ended 的反馈示例：记录可查看的到访结果；不得虚构通用条件类型，复用当前 NCS 条件池/事件记录或本次来访上下文。
- 增加一个单独测试用延迟到店配置和全空配置 fixture，检验预留与缺省；不是批量新增正式剧情。

只做结果的预约/到场事件不应弹空窗口。若当前 Presenter 不支持，补充无内容结果事件完成路径，同时保留带内容/选项的事件原有事务语义。

## 11. 验收与交付证据
